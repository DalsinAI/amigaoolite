## Compilation and first full link evidence

1. Initial whole-source audit: 237/242 files built; 5 failed. Previously qualified GFOS CPU/log and OpenGL patches resolve two. `patches/oolite/0004-gfos-polygon-glu.patch` supplies actual GFOpenGPU SGI GLU declarations for Oolite polygon tessellation; `patches/oolite/0005-gfos-miniz-stdio.patch` uses AmigaOS-supported `ftell/fseek` rather than unavailable `ftello/fseeko`. The fifth was Oolite's original Vorbis API dependency: genuine **libogg 1.3.5 and libvorbis 1.3.7** were built as temporary link-qualification compatibility dependencies. Production must instead integrate AkikoPlus `media.decode/1`, with GFOpenDatatypes fallback, as documented in `docs/OOLITE-PLATFORM-OFFLOAD-PLAN-20261118.md`. Do **not** silently count the temporary Vorbis link as the final media architecture.
2. Link resolved actual GFOpenGPU SDL3/OpenAL/SGI GLU, target SpiderMonkey 1.8.5 archive, GNUstep Foundation, native Objective-C runtime, libffi, PNG/zlib, POSIX socket/pthread and original GFOS OXZ extraction. The existing Foundation archive lacked a usable armap; reindexing a **scratch copy** with the target `ranlib` fixed many undefined Objective-C classes. A missing native NSMessagePortNameServer object requires real `sys/socket.h` while preserving ObjC `BOOL` (`patches/gnustep/0001-gfos-messageport-objc-bool.patch`). The original GNUstep NSMessagePort object, not present in the static archive, was linked explicitly. No fake class symbol definitions were introduced.
3. The full `m68k-amigaos-g++` **link returned 0**, generating an approximately 14 MB AmigaOS 68040 executable. The repository Makefile target `make -f Makefile -f build/full-link.mk oolite-full-original-link` reproduced the full link using the populated 242-object cache: RC 0, SHA256 `cb2ae4ac14ccf579d98dc1cbfdef6cafb957cf27c8c07009a5f25f7d6540bcc8`. A second fully clean 242-object rebuild **passed (242 compiler invocations, link RC0)**: SHA256 `8d049cbce80144f0599aead1f64d9295a6cfc51beb42b9a0439fe9a013c356a9`. This clean, private output is independent of the reused first 242-object cache.

## Runtime blocker (no RC yet)

Staged the real original Oolite 14 MB executable plus ~99 MB upstream `Resources` into the dedicated AmigaChrome AC090/68040 lab. **First real application launch reached the Objective-C runtime but aborted before Oolite's game menu:** `objc runtime: cannot find class NXConstantString`. The binary does contain an `___objc_class_name_NXConstantString` symbol, so missing linkage alone is not a sufficient diagnosis. Investigate Objective-C module registration, class initialization order, `-fconstant-string-class` and GNUstep runtime compatibility. An exploratory link with explicit Foundation NSObject/GSString/NSString ordering also succeeded but the later guest retry stalled (`OOLITE_ORDERED_MAIN_BEGIN` without completion); it did **not** establish a fix. After a graceful shutdown/restart of only the dedicated lab host and native bridge, the guest agent recovered and passed its command-response check. The ordered-link retry had previously hung before completion, and is archived as a failure, not a pass. A separate minimal GCC16/GNUstep Foundation guest executable containing `@"Oolite"` also aborts **before main** with `objc runtime: cannot find class NXConstantString`, demonstrating a shared Objective-C literal registration problem. The existing canonical GFOpenGNUstep `foundation_smoke_68040` (uses dynamic `[NSString stringWithUTF8String:]` and `GSInitializeProcess`) passes in the same recovered guest, RC0. A second minimal probe explicitly linking GSString/NSString/NSObject objects hung before main; that is not a fix. GFOpenGNUstep release evidence says applications need `GSInitializeProcess`, so new `patches/oolite/0006-gfos-gnustep-process-bootstrap.patch` adds this to original SDL main under `OOLITE_GFOS`. Rebuilt full 242-source application using this guarded patch linked RC0, SHA256 `384b30a6ece7b4efc7158cf982b20749acd4865a0de2d5213688046450c4982c`. This new app **has not yet passed original Oolite guest startup**; pre-main constant-string registration remains a separate blocker. The canonical GFOpenGNUstep smoke suite uses `--whole-archive` for class registration, not our current ordinary static library extraction; investigate whole-archive/constructor behaviour without fake class stubs. Do not misrepresent the second queued/stalled run as a pass.
